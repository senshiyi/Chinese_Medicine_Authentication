## 适用顺序

用户明确命名/位置/结构 → 工具要求与现有项目约定 → 课程/专题规则（2.4）→ 本文通用默认。具体场景规则覆盖通用默认；不为风格一致批量迁移已有工程。代码命名遵循对应语言惯例，例如 Python 使用 snake_case。

## 一、通用原则

1. **见名知意**：名称应准确表达其用途，避免 `a`、`b`、`tmp` 等无意义命名。
2. **一致性优先**：同一项目中统一风格，不混用不同命名约定。
3. **简洁但不缩略**：用完整单词，避免生僻缩写（`cnt` → `count`，`ctx` 这类广泛接受的除外）。
4. **避免歧义**：不同含义的实体使用不同名称，不做"一词多义"。
6. **分隔符语义区分**：`-`（短横线）用于标识来源/翻译中的复合形容词内部连接（如 `Self-made`、`Real-time`）；`_`（下划线）用于分隔不同语义单元（如 `Minecraft_Self-made_Mods`）。原则：先看一个词是否来自翻译的复合词（用 `-`），再在各语义块之间用 `_` 连接。

5. **中文优先使用拼音或英文**：中文命名的文件/变量在跨平台和脚本中可能出问题，建议用英文或拼音。

## 二、文件与目录命名

### 2.0 项目内部标准目录结构

> 适用于尚无既定结构的新课程、资料或实验项目；按实际用途分类，仅创建有内容的标准文件夹。软件仓库和用户自定结构沿用现有约定。

**三层结构**：

```
<项目>/
└── <用途分类>/              ← 如：教材、实验、作业
    ├── Cache/              ← 生成代码、临时脚本、可重建产物
    ├── Files/              ← 正式产出、可提交文件
    ├── Models/             ← 训练产出的模型权重、checkpoint
    ├── References/         ← 参考资料、只读文档
    └── Results/            ← 评估结果、预测输出、实验数据
```

**示例**：

```
Multivariate_Statistical_Analysis_groupwork/
├── 教材/
│   ├── Cache/
│   ├── Files/
│   ├── Models/
│   ├── References/
│   └── Results/
├── 实验/
│   ├── Cache/
│   ├── Files/
│   ├── Models/
│   ├── References/
│   └── Results/
└── 作业/
    ├── Cache/
    ├── Files/
    ├── Models/
    ├── References/
    └── Results/
```

**用途分类参考**：

| 分类 | 说明 |
|------|------|
| `教材/` | 教材内容、笔记、课件相关 |
| `实验/` | 实验报告、实验数据、实验代码 |
| `作业/` | 课后作业、习题解答 |

**使用规则**：
- 采用本结构的资料项目先按实际用途建立分类目录，再按需在分类下建立 `Cache/`、`Files/`、`Models/`、`References/`、`Results/`
- `Cache/` 仅存放确认可重建且不是唯一副本的内容；清理仍需符合当前授权，`Files/`、`Models/`、`References/`、`Results/` 应妥善保管
- 采用资料分类结构时避免混放业务文件；源码、清单和配置按框架规定的位置保留
- **按需创建**：`Cache/`、`Files/`、`Models/`、`References/`、`Results/` 仅在对应分类下有实际内容时才创建，不预设空文件夹

**文件类型分类规则**：

| 文件夹 | 放入内容 | 典型文件 | 可否自动清理 |
|--------|----------|----------|:---:|
| `Cache/` | 编译产物、构建输出、生成代码、临时脚本、中间文件 | `.class` `.o` `.exe` `node_modules/` `build/` `dist/` 代码生成脚本 | ✅ 确认可重建、非唯一副本且在授权范围内 |
| `Files/` | 手写源码、正式文档、提交产出 | `.java` `.py` `.md` `.docx` `.txt` | ❌ 不可自动删除 |
| `Models/` | 训练产出的模型权重、checkpoint、预训练参数 | `.pth` `.pt` `.h5` `.onnx` `.pkl` | ❌ 不可自动删除 |
| `References/` | 外部参考资料、只读文档、图片素材 | `.pdf` `.png` 参考论文 课件 | ❌ 不可自动删除 |
| `Results/` | 评估结果、预测输出、实验数据、图表、指标报告 | `.json` `.txt` `.csv` `.xlsx` `.png` | ❌ 不可自动删除 |

> **核心原则**：临时生成脚本、编译输出等可重建中间产物归 Cache；正式文档或代码包归 Files；训练权重归 Models；评估和预测产物归 Results；外部资料归 References。生成方式不决定是否为正式产出。不确定归属时保留在原位置或非清理区，不能仅因不确定就放进 Cache。

### 2.1 目录命名

| 场景 | 规则 | 示例 |
|------|------|------|
| 已有项目或框架目录 | 沿用既有约定 | `src/utils/` |
| 新通用软件仓库 | kebab-case | `my-project/` |
| 新资料子目录 | snake_case 或明确中文分类 | `reference_data/`、`教材/` |
| 课程/专题交付 | 使用 2.4 专用格式 | `Machine_Learning_project/` |

避免新建含空格目录；不要为此改动用户指定或已有路径。

### 2.2 文件命名

| 文件类型 | 命名风格 | 示例 |
|----------|----------|------|
| 普通代码文件 | 与对应语言约定一致 | `user_service.py`、`UserService.java`、`user-service.ts` |
| 配置文件 | `kebab-case` 或工具约定 | `.eslintrc.json`、`docker-compose.yml`、`tsconfig.json` |
| 文档 / Markdown | `kebab-case` 或中文 | `README.md`、`api-design.md`、`命名规范文档.md` |
| 静态资源 | `kebab-case` 或 `snake_case` | `hero-banner.png`、`logo_dark.svg` |
| 测试文件 | `<被测文件名>.test.<ext>` | `utils.test.ts`、`user_service_test.py` |

### 2.3 特殊约定

- **README 一律大写**：`README.md`
- **入口文件按框架约定**：`index.ts`、`main.py`、`App.jsx`
- **不要用空格**：Windows 允许但跨平台不友好，分隔符按 2.1 的场景选取，文件遵循语言或文档约定。
- **分隔符语义**：`-` 用于复合形容词内部（如 `Self-made`），`_` 用于语义单元之间（如 `Minecraft_Self-made_Mods`）。参见通用原则第 6 条。

### 2.4 模块化项目命名（课程 / 专题）

> 每个模块/课程的项目，文件与目录均以该模块的英文全称作为前缀，使用 **混合分隔符风格**（各词首字母大写 + 复合形容词内部用 `-` + 语义单元间用 `_`），后接类型和日期。

**格式**：
```
<模块英文名>_<类型>_<月份>_<日期>.<扩展名>
<模块英文名>_<类型>/                    （目录，无需日期）
```

**字段说明**：

| 字段 | 说明 | 示例 |
|------|------|------|
| 模块英文名 | 模块/课程的英文全称，语义单元间 `_` 分隔，复合形容词内部 `-` 连接 | `Minecraft_Self-made_Mods`、`Multivariate_Statistical_Analysis` |
| 类型 | `homework` / `groupwork` / `lab` / `project` / `exam` / `notes` | `project` |
| **月份** | 数字，`1`~`12`（不带前导零） | `6` |
| **日期** | 数字，`1`~`31`（不带前导零） | `10` |

**示例**：

| 场景 | 命名 |
|------|------|
| Minecraft 自创 Mods - 项目 | `Minecraft_Self-made_Mods_project/` |
| 多元统计分析 - 个人作业 | `Multivariate_Statistical_Analysis_homework_6_10.ipynb` |
| 多元统计分析 - 小组作业 | `Multivariate_Statistical_Analysis_groupwork_6_10.docx` |
| 多元统计分析 - 小组作业目录 | `Multivariate_Statistical_Analysis_groupwork/` |
| 机器学习 - 实验报告 | `Machine_Learning_lab_5_20.docx` |
| 数值分析 - 笔记 | `Numerical_Analysis_notes_4_15.md` |

**常见模块英文名参考**：

| 中文名 | 英文名 |
|--------|--------|
| Minecraft 自创 Mods | `Minecraft_Self-made_Mods` |
| 多元统计分析 | `Multivariate_Statistical_Analysis` |

## 三、代码命名

### 3.1 通用规则

| 元素 | 风格 | 示例 |
|------|------|------|
| 变量 / 属性 | `camelCase` | `userName`、`totalCount`、`isLoading` |
| 常量 | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT`、`API_BASE_URL` |
| 函数 / 方法 | `camelCase`（动词开头） | `getUserById()`、`handleClick()`、`fetchData()` |
| 类 / 接口 / 类型 | `PascalCase`（名词） | `UserService`、`HttpClient`、`OrderStatus` |
| 枚举值 | `PascalCase` | `OrderStatus.Pending`、`Color.Red` |
| 私有成员 | 前缀 `_` 或 `#` | `_internalState`、`#privateField` |

### 3.2 布尔值

- 以 `is`、`has`、`can`、`should` 开头：`isVisible`、`hasPermission`、`canEdit`、`shouldUpdate`
- 避免否定式命名：`isDisabled` ✅ / `isNotEnabled` ❌

### 3.3 回调与事件

- 事件处理函数以 `handle` 或 `on` 开头：`handleSubmit`、`onClick`、`onDataLoaded`
- Props 中的回调以 `on` 开头：`onChange`、`onClose`

### 3.4 临时变量

- 循环索引用 `i`、`j`、`k` 可接受
- 解构临时变量要有意义：`const { name, age } = user` ✅

## 四、项目与仓库命名

| 规则 | 示例 |
|------|------|
| 新通用软件仓库使用 `kebab-case`；课程/专题按 2.4 | `my-awesome-app`、`codex-skills` |
| 无既有约定的新通用软件仓库默认英文、小写、短横线 | `my-awesome-app` |
| 避免无意义后缀 | ❌ `project1` ❌ `test123` |

## 五、数据库命名

| 元素 | 风格 | 示例 |
|------|------|------|
| 表名 | `snake_case`、复数 | `users`、`order_items` |
| 列名 | `snake_case`、单数 | `created_at`、`user_id`、`is_active` |
| 主键 | `id` | `id` |
| 外键 | `<表名单数>_id` | `user_id`、`order_id` |
| 索引 | `idx_<表>_<列>` | `idx_users_email` |
| 唯一约束 | `uq_<表>_<列>` | `uq_users_phone` |

## 六、Git 命名

| 元素 | 风格 | 示例 |
|------|------|------|
| 分支名 | 用户/项目指定前缀优先；Codex 默认 `codex/` + kebab-case，其他环境可用类型前缀 | `feat/user-auth`、`fix/login-bug`、`docs/api-guide` |
| Commit 信息 | Conventional Commits | `feat: 添加用户登录功能`、`fix: 修复分页越界` |
| Tag | `v<semver>` | `v1.0.0`、`v2.1.3-rc1` |

### Commit 类型前缀

| 前缀 | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 修复 Bug |
| `docs` | 文档变更 |
| `style` | 格式调整（不影响逻辑） |
| `refactor` | 重构 |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `chore` | 构建/工具/依赖 |
| `ci` | CI/CD 配置 |

## 七、快速检查清单

- [ ] 一眼能看出这个名称是干什么的吗？
- [ ] 有没有用完整单词而不是生僻缩写？
- [ ] 命名风格是否与同项目其他文件一致？
- [ ] 有没有用空格或特殊字符？
- [ ] 布尔值是否以 `is`/`has`/`can`/`should` 开头？
- [ ] 函数名是否以动词开头？
- [ ] 课程/模块文件是否以模块英文名开头？（见 2.4）
- [ ] 复合形容词（如 `Self-made`）内部是否用 `-`，语义单元间是否用 `_`？（见通用原则第 6 条）
